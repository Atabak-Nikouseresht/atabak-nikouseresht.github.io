FLAGSHIP CASE STUDY · FRAUD RISK

IEEE-CIS Fraud Detection

Can a model help prioritize a limited review queue for rare fraudulent transactions?

Compared fixed Logistic Regression and XGBoost on transaction-only data using chronological model-training, calibration and final-evaluation partitions.

0.888ROC-AUC · temporal holdout
0.480Average precision · temporal holdout
0.871Precision · top 1% batch review

Decision relevance: the budget comparison shows how ranking performance translates to the composition of a limited review queue.

PythonXGBoostTemporal evaluationCalibration
Evaluation design & limitations

The chronology assigns 354,324 rows to model training, 118,108 to calibration and 118,108 to final evaluation. Full-file label validation occurred before final metrics, so this was not a physically sealed-label experiment.

Anonymized feature timing and label maturation remain uncertain; repeated card attributes are not verified customer IDs. This retrospective result is not entity-disjoint validation, an operational policy, deployed performance or evidence of savings.

Fraud Detection Streamlit App

Method

Model limitations & local run

Run locally: with Python 3.11.16, run uv sync --locked --no-dev, then uv run streamlit run app/fraud_app.py from the repository root.

The form accepts eight fields, while the legacy fitted transformer uses six and drops two derived balance-difference features. The artifact predates the corrected notebook methodology; training provenance and real-world predictive performance are not established.
